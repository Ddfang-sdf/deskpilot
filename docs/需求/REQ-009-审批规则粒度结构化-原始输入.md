## 1. 背景与战略裁定

对比分析发现:Codex 的审批机制有「规则持久化」维度——人类批准一次后
可选择把「同类命令」固化为持久规则(prefix 模式匹配),后续同类动作
免审批。DeskPilot 已有「批准一次/此后同类允许/永久加入/拒绝」四按钮
雏形,但「同类」的判定粒度是**整应用×级别**,比 Codex 的命令模式粒度
粗一个数量级。

粒度粗的代价是双向的:要安全就审批疲劳(每次都问),要省事就过宽授权
(整个应用 L 级全开)。sdfang 裁定采纳「审批规则结构化」方向,立本单。

## 2. 现场实证(2026-09-22 代码亲验)

| 位置 | 事实 |
|------|------|
| `policy.yml` | 白名单条目= `{ process, max_level }`,粒度=**进程×级别**,无任何参数/窗口/动作模式维度 |
| `deskpilot/policy.py:55-105` | policy.local.yml 合并逻辑已支持墓碑(撤回即墓碑,不回流)、显式覆盖——**账本基础设施已就绪,缺的是更细的条目结构** |
| `deskpilot/models.py` | `TOOL_LEVELS` 把 29 个工具分 L1/L2/L3,级别是工具的固有属性,不可按场景细化 |
| REQ-007 §2 文案盘点 | 审批窗四按钮(批准一次/此后同类允许/永久加入/拒绝)已存在,但「此后同类允许」的「同类」语义=当前实现的应用级,非规则级 |
| `deskpilot/enforcement.py` | 审批描述带动态模板(进程名/路径槽位),说明**上下文要素(进程/路径/窗口标题)在执行侧已可得**,缺的只是规则匹配层 |

## 3. 初版方案(方向,评审后细化)

| 项 | 设计方向 |
|----|---------|
| A | 规则结构:`{ process, tool 或 level, 参数模式(可选), 窗口标题模式(可选), 动作=allow/deny, 来源=人类审批按钮 }`,写入 policy.local.yml(沿用「人类裁决写入独立用户文件」铁律) |
| B | 匹配语义:具体规则优先于整应用级条目;无命中=落回现行级别判定;**deny 规则优先于 allow**(显式拒绝永不被宽规则覆盖,fail-closed) |
| C | 审批窗按钮语义升级:「此后同类允许」的「同类」=本次调用的{进程+工具+关键参数模式},弹窗文案须**明示将固化的规则内容**(人类知道自己在批准什么规则) |
| D | 白名单管理窗增加「规则」视图:逐条列出、可移出(移出即墓碑,沿用 ISS-0072 语义) |
| E | 审计:每次规则命中记录命中的是哪条规则(可解释性——事后能回答「这次为什么没弹窗」) |

## 4. 硬约束(需求分析时必须逐条落进方案)

1. **fail-closed 不可动**:任何规则解析失败/模式非法=按无规则处理(落回现行判定),禁止静默放行;
2. **墓碑语义兼容**:新粒度条目同样支持撤回墓碑,不得因旧配置回流复弹(ISS-0072 已立);
3. **人类裁决账本不动**:policy.local.yml 仍只由人类审批动作写入,AI 无任何写路径;
4. **规则可解释**:审计必须能还原每次放行/拒绝的规则依据,无依据的放行视为缺陷;
5. **范围控制**:本单只做「允许规则的粒度细化」;**不做**「AI 自申请规则」「规则模板市场」等智能面,出现即出范围;
6. **交叉面清单必附**:本单触及 policy 合并、审批窗、enforcement、白名单管理窗、审计五面,测试设计阶段交叉组合爆炸风险高,§2.1 清单从严。
