## 1. 背景与战略裁定

2026-09-22,sdfang 要求对 DeskPilot 与 Codex 做对比分析。结论:二者
不同层——DeskPilot 是工具层(MCP server),Codex 是 Agent 本体,**互补
而非竞争**;Codex、Claude Code、Cursor 均为潜在客户。

分析同时发现:Codex 会读取 MCP server 初始化时返回的 `instructions`
字段,当作该 server 的「使用须知」一并纳入上下文。即 **server 可以自带
一份「该怎么用我」的说明书,客户端 Agent 天生就能读到**。DeskPilot 已有
此字段但内容极薄(见 §2),大量规矩散落在外部文档与错误消息里,Agent
只能事后踩坑学习。

sdfang 裁定:此建议连同其余四条(REQ-009~REQ-012)**全部采纳**,各立
原始输入单。

## 3. 初版方案(方向,评审后细化)

| 项 | 设计方向 |
|----|---------|
| A | instructions 扩写为结构化使用须知:危险操作审批语义(会弹窗/人类点头/超时拒绝/约 90s)、急停冻结语义(冻结时全拒/解冻仅人类)、白名单与入白三态、daemon 与 stdio 形态差异、错误码自愈总原则 |
| B | **单源化**:文案注册进既有单源体系(参照 ISS-0015 描述注册表纪律),禁止在 mcp_server.py 里再堆硬编码长串;与 i18n 的关系按 REQ-007 裁定——受众是 AI,语言策略留评审(英文优先或双语并列) |
| C | 长度预算约束:instructions 进客户端上下文,须定上限(评审定,建议 ≤500 词)并加钉测试防膨胀;工具描述不复读,服务说明书只讲跨工具全局规矩 |
| D | 验收:用真实 MCP 客户端(至少 Codex、Claude Code 之一)冷启动会话,**不给任何外部文档**,观察 Agent 首次遭遇审批/冻结/白名单拒绝时的反应是否符合说明书预期 |

## 4. 硬约束(需求分析时必须逐条落进方案)

1. **不改任何安全语义**:instructions 只是告知,四道闸行为零变化;
2. **单源纪律**:文案注册表化,缺注册即钉红(与 ISS-0015/REQ-007 同纪律);
3. **受众=AI**:按 REQ-007 §3 裁定,MCP 面文案语言策略独立于界面 i18n,需求分析时终裁;
4. **跨客户端措辞中立**:不得出现「Claude」「Codex」等特定客户端名,说明书面向一切 MCP 客户端;
5. **可验证**:必须有「冷启动 Agent 实测」验收环,禁止仅以文本存在性收口。
