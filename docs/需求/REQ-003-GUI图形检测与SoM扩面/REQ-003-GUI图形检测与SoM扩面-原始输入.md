## 1. 分离裁定的原话与语境

ISS-0044(无文字图形定位困难)在方案评审时收敛为两条互补小改动:
① `get_ui_tree`/`click_element` 的 `control_type` 过滤寻址;
④ `click_text` 的文字锚点偏移。

这两条覆盖了"UIA 可见控件"与"带文字标签控件"两个主场景。
**但"任意图形"(自绘界面 / 纯图标 / 画布)仍无解**。sdfang 2026-09-09 裁定:

> "我们都要做。"

于是检测模型 + SoM 扩面从 ISS-0044 分离,另立 REQ-003。分离理由(承 ISS-0044 §2.1):

- ①②④ 三个小改动均有业界实证,可在既有工具面上增量落地,不新增依赖;
- 检测模型路线引入**模型工程 + 许可地雷 + 打包成本**三重新面,与前三者
  不是一个量级的工程决策,混在一单里会拖住小改动的交付;
- 但检测路线是该场景的**唯一业界正路**——不能因为难就不做。

## 2. 无文字图形定位的通道盘点(实证)

ISS-0044 §1 的通道对照表,是"检测模型路线不可回避"的直接证据:

| 通道 | 对文字 | 对无文字图形 |
|------|--------|-------------|
| OCR | [text, position] 直接给 | **无锚点** |
| UIA(get_ui_tree) | name 好认 | 全树翻找 unnamed 难辨认;**自绘界面(Electron/游戏/画布)不可见** |
| SoM(get_clickable_map) | 编号标图 | **仅限 UIA 可交互元素** |
| template_match | 模板找图 | **鸡生蛋**:无模板需先有图,无图需先知位置 |

前三条通道在"自绘界面"这一格上同时失效,且这不是调参能解决的问题——
它是"没有可用的图形区域供给"这一根本缺口的表征。REQ-003 要补的就是
**图形区域供给**这一环。

## 3. 业界调研证据链(原文亲验,承 ISS-0044 §2.1)

| 路线 | 代表 | 关键证据 | 对本单 |
|------|------|---------|--------|
| 纯视觉检测模型 | 微软 OmniParser(arXiv 2408.00203,191+ 引用) | YOLOv8 图标检测(67K 截图微调)+ BLIP 图标描述 + OCR + SoM;**V2 ScreenSpot-Pro SOTA 39.5%** | **路线有效,但有天花板**——39.5% 是 SOTA,说明"纯检测"不是银弹,必须与 UIA 互补 |
| 组合方案(研究最优) | FSE2020(arXiv 2008.05132)作者方案 | §4.2 原文亲验:GUI 专用传统法 + ResNet50 分类器 + EAST 文本检测,**非文本 F1 = 0.523**(vs 最优基线 0.438),全部 F1 = 0.573(vs 0.388) | 证明**检测模型路线有效**;同时说明该路线是"工程项目"级投入 |
| 传统轮廓法 | REMAUI / Xianyu | FSE2020 Table 2(IoU>0.9):**REMAUI F1 = 0.201、Xianyu F1 = 0.154** | **死刑**——纯轮廓法不做 |
| SoM 标记提示 | 微软 SoM(arXiv 2310.11441,840+ 引用) | **裸坐标直接输出效果差(REC 25.7);是标记而非坐标解锁定位** | **SoM 扩面是该路线的正确终点形态**——检测出区域只是半程,必须进编号空间 |

**证据链的推论**:
1. 纯轮廓法(几何启发式)数据证明不可行(F1≈0.15~0.20),排除;
2. 检测模型路线有效但天花板明确(非文本 F1≈0.52 / ScreenSpot-Pro 39.5%),
   因此**不是** UIA 的替代品,只能是与 UIA 互补的补充通道;
3. SoM 论文的核心结论(标记解锁定位,裸坐标差)决定了:检测出的区域
   **必须进入 `get_clickable_map` 的编号空间**才算真正可用——
   否则 AI 拿到的仍是一堆需要自己拼的坐标,回到 ISS-0044 的老路。

## 4. 许可与成本的已知情报(地雷识别,定案见决策记录)

| 面 | 已知情报 |
|----|---------|
| 许可 | OmniParser 的检测模型**继承 YOLOv8 的 AGPL 许可**,与 deskpilot 的 **MIT** 冲突——地雷已识别 |
| 打包 | deskpilot 交付形态是 **PyInstaller 单文件 exe**;模型权重体积对解包启动耗时与分发体积的影响量级待估 |
| 耗时 | 全屏 OCR 已有先例:**5.2s 首推超 L0 的 5s 预算**(2026-09-05 实证,ISS-0039 已用 per-tool 覆盖到 12.0s);检测模型推理量级待估 |
| 安全面 | 若走远程推理,截图将**出本机**——与 deskpilot 现有"只读本机"的安全面冲突 |
| 无先例面 | 这是 deskpilot 首次引入**运行时可选外部模型组件**——无既有形态可循,形态本身是决策点 |

## 6. 场景清单(验收上下文)

| 编号 | 场景 | 为什么现有通道做不到 |
|------|------|-------------------|
| SC-1 | 自绘界面(Electron/游戏/画布)里的纯图形按钮:AI 要看图找到它 | UIA 树对该区域无节点;OCR 无文字 |
| SC-2 | 图标工具栏:一排无文字的图形按钮,AI 要"点第 3 个" | OCR 无锚点;UIA 若暴露也是 unnamed,难以辨认 |
| SC-3 | 画布上的图形元素:AI 要拿到图形区域的 rect 以规划拖拽/绘制 | 无 UIA 节点;模板匹配鸡生蛋 |
| SC-4 | 混合界面:部分有 UIA、部分自绘——AI 要**一次调用**拿到统一编号的完整图 | 两个通道需 AI 自己拼,回到 ISS-0044 的"自建链路"老路 |
