## 一、假设公式与验证设计

**假设**:`screen = 内容区矩形原点 + viewport_css × devicePixelRatio`

- 内容区矩形 = `Chrome_RenderWidgetHostHWND` 的 GetWindowRect(物理像素,自动含工具栏偏移;本机实测主窗 [100,50,1300,950] 时内容区 [112,130,1288,938],工具栏 80px);
- viewport_css = `DOM.getBoxModel` content 四顶点中心(实测为 **viewport 相对 CSS 像素**,滚动后自动变化,与 getBoundingClientRect 同基准);
- 命中判定:页面内计数器 `Runtime.evaluate` 读回(点击真生效);
- 像素误差真值:daemon 物理窗口截图 + 按钮纯色像素扫描(完全独立于公式的第三条测量路径);
- CSS 侧交叉验证:`DOM.getNodeForLocation(css 坐标)` 解析回目标节点。

## 二、穿刺矩阵(32 格;误差=计算屏幕点 vs 截图真值中心)

| 阶段 | dpr | 格数 | 命中 | 误差(px) |
|------|-----|------|------|-----------|
| 基线 zoom100 无滚动 | 1.0 | 5/5 | **全中** | 0.71(纯取整) |
| 真 zoom(ctrl+= ×3 → 150%) | **1.5** | 5/5 | **全中** | 0.71 |
| Emulation 指标覆盖 1.5(存证格) | 报 1.5 | 0/2 | 全 miss | 47.0 / 算到窗外被 OUT_OF_BOUNDS 拦 |
| 滚动(逐钮 scrollTo 入视野) | 1.0 | 4/4 | **全中** | 0.71 |
| force-device-scale-factor=1.25 | 1.25 | 5/5 | **全中** | 0~0.5 |
| 1.25 + 滚动 | 1.25 | 3/3 | **全中** | 0.5 |
| force-device-scale-factor=1.5 | 1.5 | 5/5 | **全中** | 0.5~0.71 |
| 1.5 + 滚动 | 1.5 | 3/3 | **全中** | 0.5~0.71 |

**真实渲染条件下 30/30 全中,最大误差 0.71px(= √0.5² 整数取整噪声)。公式无需任何修正项。**

## 三、dpr 行为实录(zoom 改变 dpr 吗?)

**改变,且如实跟随。** 三种「缩放」机制实测三种行为:

| 机制 | dpr 实测 | 物理渲染 | 公式适用? |
|------|----------|----------|-----------|
| 真·浏览器 zoom(rawKeyDown ctrl+= ×3:100→110→125→150%) | 1→**1.5**,innerWidth 1176→784(=÷1.5) | 物理放大(按钮 92×36→138×54px) | **成立**(0.71px) |
| `--force-device-scale-factor=1.25/1.5` | 1.25/1.5,innerWidth 同比收缩 | 物理放大 | **成立**(≤0.71px) |
| `Emulation.setDeviceMetricsOverride` | 报 1.5(与真 zoom 叠加时实测 2.25,乘性关系) | **不变**(虚拟仿真) | **不适用**——按报出 dpr 计算误差 47~662px |

记录要点:
- 页面 zoom 在 Chromium 里就是以 dpr 实现的——公式 dpr 项天然覆盖「系统 DPI × 页面缩放」两因子,假设成立;
- CDP 键事件模拟 zoom 快捷键必须用 **rawKeyDown**;`keyDown` 变体实测 dpr 纹丝不动(不触发浏览器加速器);
- CDP **没有**直接设 zoom 的接口(zoom 是 per-origin content setting);
- Emulation 指标覆盖只改页面所见,不改物理映射——**任何坐标验证都禁止用它模拟缩放**。

## 四、公式终稿(无需修正)

```
screen_x = content_rect.left + css_x × dpr
screen_y = content_rect.top  + css_y × dpr
```

- `content_rect` = 内容区宿主窗口(Chrome_RenderWidgetHostHWND)物理矩形,**每次现取**(窗动即变,取一次 <1ms);
- `css_*` = getBoxModel 中心(viewport CSS 像素,滚动后须重取);
- `dpr` = `window.devicePixelRatio`,现取;
- 取整:round 到整数物理像素,误差上界 √0.5² ≈ 0.71px,实测与理论一致。

## 五、侦查中抓到并已排除的两个伪异常(如实记录)

1. **「14.5px 误差」假象**:1.25 档滚动后点 s_c 未中——根因是滚动后 s_c 恰好滚到 fixed 定位的 b_c 按钮背后,物理命中测试落在**最上层元素** b_c 上(b_c 计数 +1 坐实)。公式没错,是**页面内遮挡**问题 → v1 设计含义:`browser_get_rect` 应附 `document.elementFromPoint` 遮挡自检(返回值≠目标即警示),物理点击落的是顶层元素,这一课与桌面域「遮挡可点/不可点」语义直接相通。
2. **「32px 误差」假象**:真值扫描把相邻按钮边缘色桥接进掩码——行/列密度门槛修法后归零;并保留 ±150px 近点 ROI。测量方法学教训,已固化进脚本。

另有两条 daemon 强制层正面存证:override 档算错的落点被 **OUT_OF_BOUNDS**(落点在绑定窗口矩形外)与 **WINDOW_OCCLUDED**(被 kimi code.exe 遮挡)拦截——强制层对坐标类误射的防护实测有效。

## 六、老花镜模式成立性结论

**成立。** `browser_get_rect` 可以直接吐虚拟桌面物理坐标:CSS→物理映射在 dpr 1.0/1.25/1.5、真 zoom、滚动组合下全程 ≤0.71px,精度与 UIA rect 同级。落地口径:

1. 工具内聚三步:CDP getBoxModel(现取)→ 读 dpr(现取)→ 读内容区宿主矩形(现取)→ 吐物理坐标;不缓存任何一项;
2. 物理点击仍走 daemon 强制层(attach/token/前台/遮挡闸),浏览器域与桌面域同一套写护栏;
3. 附遮挡自检(elementFromPoint)与「几何变化后重取」提示,与桌面域「窗口几何变化后坐标作废」同规;
4. 已知边界(如实):页面内 fixed 遮挡时坐标正确但命中顶层元素(须靠自检暴露);Emulation 覆盖态 dpr 失真(受管实例正常浏览不会出现)。
