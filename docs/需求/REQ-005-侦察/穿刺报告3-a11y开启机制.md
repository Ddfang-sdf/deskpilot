## 〇、头条结论(对穿刺 2 的修正)

穿刺 2「UIA 通道对 Chromium 网页内容覆盖=0」**只在两个特定条件下成立**:①从主窗根 walk(永远只见壳);②对内容宿主窗首查即走(树尚未异步灌入)。
**真相:Chromium 的网页 a11y 是懒启用的——任何 UIA 客户端直接查询内容宿主窗(`Chrome_RenderWidgetHostHWND`)即触发开启,约 2~3 秒后全量树灌入,之后进程生命周期内持久可读。零全局信号、零注册表、零用户操作。**

关键细节:
- 触发源 = **对 render widget HWND 的 UIA 查询本身**(ControlFromHandle+GetChildren,WM_GETOBJECT 直达渲染宿主);从主窗根 walk(r07 懒启用实验,8s 三采)**永不触发**——壳与内容是两个世界;
- 触发后**闩锁(latch)**:树不随信号撤销而回落(SPI 还原后 0/3/8s 复采均 128,进程退出才消失);
- flag 档节点 189 > 懒启用档 170:从头全开比懒启用灌入更全(约 +11%)。

## 四、副作用实录(任务⑥)

- **SPI 开启期间**:顶层可见窗口数 25→25(无窗口异常);本机无读屏软件,无抢占;**已知全局性**(文献级+实测推论):所有 Chromium 进程(含用户日常 Edge×15)会 latch-on a11y 至各自退出——渲染进程常驻额外开销;Office 等监听该信号的应用可能改变动画行为(本机未复现实测,标文献级)。
- **闩锁即「用完即关」的反面**:SPI 可以用完即关(信号层面已还原),但**浏览器进程内的 a11y 不随关而撤**——对用户日常浏览器而言,一次脉冲=余生开启。这正是放弃 SPI 路径的决定性理由:裸查询触发**只作用于目标渲染进程**,零全局涟漪。
- 注册表 B 路径若用,键残留即改变用户所有 Edge 实例行为(本轮已删,edge://policy 无残留)。

## 七、落地路径建议(任务④)

1. **「让用户自拉浏览器被看清」零配置达成**:不需要 SPI、不需要注册表、不需要引导用户开任何开关——DeskPilot 对目标浏览器窗口 `EnumChildWindows` 找 `Chrome_RenderWidgetHostHWND`,对其发 UIA 查询,**等 2~3s 复走**,网页内容即全量可读(rect 直出屏幕坐标,0.11px 级)。引导文案形态从「请开启辅助功能」**降级为「首次感知浏览器需 2~3 秒初始化」**(纯等待提示,无用户动作)。
2. **受管实例**(DeskPilot 自拉):拉起即带 `--force-renderer-accessibility`——免触发延迟、节点更全(189 vs 170),零成本,应作为受管实例默认参数。
3. **get_ui_tree 适配**:UIA 内容路线三要素——①对 render widget hwnd 直查(主窗 walk 永远只见壳);②首查后延迟复走(懒灌入);③daemon 深度帽=10 对内容够用(内容根起算)但节点数略低于直读(128 vs 170,StaticText 类被裁),如需全文本可加深。
4. **与 CDP/AXTree 的关系重估**:UIA 路线(开启后)语义≈九成、坐标等效、且**不挑 Chromium 家族**(Firefox 同理可期)——感知路由 v1 的「①CDP 层」必要性下降为「需要 CSS 选择器/evaluate 读回/滚动控制等 DOM 能力时才用」;纯「看清+点击」UIA 即可。路线 A(自研 CDP 子集)与 UIA 直查的最终分工,建议进 REQ-005 路线终裁材料(本报告 + 穿刺 1/2 为证据)。
5. **永不使用**:SPI(全局 latch 副作用,且无增益)、策略键 B(实测无效);C 仅作受管实例内的备选(不如 flag 干净)。

## 八、测量方法学教训(如实记)

本轮连续三次踩「测量通道自身的坑」:①daemon get_ui_tree 传 token 被拒(假 0);②主窗 walk 深度帽=10 恰裁在内容根(假 0);③首查即走撞上懒灌入延迟(假 0)。**凡是「覆盖=0」类结论,必须先证明测量通道在该条件下能见到非零。** 穿刺 2 报告相关结论已按本报告 §〇 修正。
