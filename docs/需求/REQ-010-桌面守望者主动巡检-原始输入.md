## 1. 背景与战略裁定

对比分析发现:Codex 有定时唤醒/状态监控机制(自动化与 heartbeat),能
「盯着某状态,变了再叫我」。DeskPilot 的常驻 daemon 已有长驻进程形态,
但语义是**纯被动**——AI 不调用,它什么都不做。AI 想实现「等保存对话框
出现再点确定」,只能 sleep+screenshot 轮询,成本与盲区双高。

sdfang 裁定采纳「守望原语」方向,立本单。核心定位一句话:**daemon 从
应答器升级为守望者,但只看不动的铁律不破。**

## 2. 现场实证(2026-09-22 代码亲验)

| 位置 | 事实 |
|------|------|
| `deskpilot/httpd.py` | 常驻 daemon(:9420)已有,单次调用约 1.2s、绑定跨调用保持——**长驻基础设施就绪,缺守望语义** |
| `deskpilot/main.py:234-236` | 热键/甩角轮询线程已是「daemon 内后台循环」先例(50ms 周期轮询 estop)——技术形态证明可行 |
| `deskpilot/main.py:317` | policy-watch 线程(配置热加载)是第二个后台循环先例 |
| `deskpilot/janitor.py` | 审计清理是第三个周期性后台任务先例 |
| ISS-0008(性能优化启动阻塞与资源占用) | 资源占用曾出事故,守望循环的周期与成本必须钉死上限 |

## 3. 初版方案(方向,评审后细化)

| 项 | 设计方向 |
|----|---------|
| A | 守望注册原语:`watch_register(条件)`——条件类型 v1 候选:窗口出现/消失(标题或进程匹配)、窗口标题变化、指定矩形区域像素变化;注册返回 watch_id |
| B | 事件投递:两通道候选——MCP notifications(协议原生,但客户端支持度待实证)/ `watch_poll(watch_id)` 拉取(兜底,协议无关);评审定主通道 |
| C | 生命周期:watch 有 TTL 与最大存活数上限;daemon 重启清空(会话语义,不入持久账本);显式 `watch_cancel` |
| D | 只读铁律:守望**只产生事件,绝不自动执行任何写操作**;事件内容=感知面数据(窗口清单/标题/区域哈希),触发后的动作仍走既有四道闸 |
| E | 资源护栏:单 watch 轮询周期下限(如 ≥500ms)、全局 watch 数上限、总 CPU 占用钉测试;超限 fail-closed(拒注册,显式报错) |

## 4. 硬约束(需求分析时必须逐条落进方案)

1. **只读感知面**:守望不产生写操作;锁屏/UAC 期间(SECURE_DESKTOP)守望同样静默——人类不可视=AI 不可感知;
2. **白名单约束不变**:守望条件的进程匹配范围不得越过白名单语义(具体边界评审定:感知是否要求目标在册);
3. **资源占用钉死**:周期下限/数量上限/CPU 上限三条钉测试,防 ISS-0008 族回潮;
4. **事件入审计**:注册/命中/取消全程 JSONL 留痕,与既有审计同册;
5. **急停语义一致**:estop 冻结期间事件暂停投递(冻结=一切停摆,含感知推送),解冻恢复;
6. **范围控制**:不做「条件触发自动动作」(IFTTT 面)——那是写操作自动化,出本单范围,如需要另立单。
