# SDD 工作原则 · 测试设计与开发(全局版)

> 定位:给任何 AI Agent 在任何项目中执行"设计驱动开发"时可照做的工作原则。
> 与语言、框架、仓库无关。本篇只讲两件事:**测试怎么设计、开发怎么推进**。
> 角色约定:**人类**=决策者(审核、拍板、身份类动作);**Agent**=执行者(分析、写文档、写测试、写实现、跑验证、汇报证据)。

---

## 1. 三条铁律(凌驾于一切细节)

1. **没有被人类审核通过的方案,不许动代码。** 方案包含:根因(带实证)、改法、约束、测试设计。
2. **先红后绿。** 先有验证用例证明"没实现/有 bug"(红),再有实现(绿);禁止"改完跑旧用例觉得没问题"——旧用例只证明没破坏已有行为,证明不了新行为正确。
3. **断言必须有出处。** 断言值由被调方法的返回值、响应体、或持久化数据**直接产出**;禁止中间转换、禁止"看起来相似"。

---

## 2. 测试设计五要素(每条用例缺一不可)

| 要素 | 含义 | 不合格示例 |
|------|------|-----------|
| **测试场景** | 本条用例覆盖什么业务/使用情境 | "测一下登录"(不是场景,是主题) |
| **测试前提** | 执行前系统必须处于的状态:环境、数据、依赖就绪条件 | 前提靠读者脑补 |
| **测试步骤** | 按序执行的操作序列,可复现 | "随便点几下" |
| **测试预期结果** | 每步及最终应观察到的结果 | "应该能成功" |
| **断言代码** | 预期结果翻译成代码后的具体断言:断哪个值、由什么直出 | 预期写成"返回正确结果",翻译不成断言 |

关键约束:**断言不是写测试代码时临时想的,是设计阶段就和预期结果一起定好的。** 预期结果翻译不成断言代码的,该用例设计不合格,打回重写。

---

## 3. 测试三层维度(由外到内,各守各的边界)

### 3.1 黑盒测试 —— 站在系统外,验"对外提供的功能"

- **禁止 import 任何函数/方法,禁止引入源码**,系统当黑箱。
- 驱动只能通过外部手段:命令行、脚本、HTTP 请求等,模拟真实使用场景。
- 断言在**系统外表面**:响应体、CLI 输出、退出码、外部可观察产物。

### 3.2 集成测试 —— 站在模块角度,验"模块间协作"

- **允许** import 公共方法/函数;**禁止打桩 mock**。
- 调用公开入口,链路必须真实**直达数据层**,不许在中间截断。
- 断言在**数据层**:落库的记录、落盘的文件内容。

### 3.3 单元测试 —— 站在方法/函数角度,验"单点逻辑"

- **允许打桩 mock**,隔离外部依赖。
- 断言在**函数层**:返回值、异常。

一句话记忆:**黑盒不碰源码(断在外表面)、集成不许断链路(直达数据层、断在落库落盘)、单元随便 mock(断在函数返回值)。**

## 4. 三阶段开发循环

### P1 —— 写测试代码

> 现在先写测试代码,验收标准:
> - 全部代码按照设计文档实现,能够编译通过。
> - 所有测试均有合理的断言,断言值由被调方法的返回值或持久化数据直接产出,不存在中间转换或推测。
> - 测试必须调用设计文档中定义的公开方法入口。设计文档中定义的纯函数(如有明确的输入输出定义)视为模块级公开函数,允许直接测试。
> - 不得跳过上层公开方法直接测试其内部未在设计文档中定义的私有方法。
> - 严禁实现业务代码。为了测试代码能够编译通过,可以先将业务代码实现成空壳代码。先于测试实现业务代码逻辑的行为,是极度不负责的。

执行要点:
- 预期结果:**新用例应红**(未实现),旧用例应绿(未误伤)。红色分布必须精确落在"未实现行为"上——红错地方说明测试写错了。
- 空壳只给签名与占位抛出,不写任何逻辑。
- 私有逻辑需要测试的:先在设计文档中提炼为公开纯函数,再测。

### P2 —— 验证测试代码

> 测试代码已生成。请基于实际的测试代码文件,逐用例确认:
> - 测试调用的入口方法与设计文档定义的方法是否一致。
> - 测试传入的参数值经过该方法的处理后,按设计文档的逻辑,能否产出测试断言的预期值。
> - 任何断言字段如果不由被调方法直接产出,标记为不一致。
> - 禁止仅凭断言文字与设计文档"看起来相似"即判定一致。

执行要点:输出逐用例核对表(用例 → 入口 → 断言值出处 → 五要素齐全性)。有一项不一致,改测试,不许将就。

### P3 —— 实现业务代码

> 现在开始实现业务代码,验收标准:
> - 全部代码按照设计文档实现。
> - 实现后必须运行测试,所有测试用例执行通过。
> - 只写业务逻辑,以文档设计为准,严禁私自简化流程和代码、严禁私自设计降级逻辑。
> - 测试用例执行不通过,应该首先检查代码实现是否有问题。如果单次运行测试失败,最多检查并修改代码 3 次。3 次后如果仍有失败,停止并汇报,附带失败日志和分析。
> - 如果评估发现测试用例代码实现不合理,立刻停止所有工作并汇报,由人决策。

执行要点:
- 失败后**先怀疑实现,不许改测试迁就**(测试不合理只能上报,不可私改)。
- 全绿后必做:跑全量套件(不只新用例)、能实盘就实盘(UI/集成路径走一遍)、保留证据(截图/日志/时序数据)。

## 5. 工作纪律(执行全过程适用)

| 纪律 | 说明 |
|------|------|
| 分析先行,实证说话 | 每条根因/结论附证据(文件:行号、日志、实测);写到机制层(为什么发生),不写现象层(发生了什么);没证据不下结论 |
| 安全路径 fail-closed | 未覆盖的情况=拒绝/显式报错,禁止静默降级;降级逻辑只能来自设计文档,严禁现场私造 |
| 破坏性/外发操作先确认 | 删除、覆盖、推送、发布、对外发送一律人类显式许可;"禁止推送"类指令长期有效直到撤销 |
| 凭证不越权 | 密钥/令牌只入约定配置位,不入库、不打印;身份类动作(扫码/人脸/支付)永远人类执行 |
| 范围控制 | 执行中发现的相邻问题:记录并上报,不顺手改(防范围蔓延与回滚困难) |
| 汇报用证据说话 | 绿=测试全过数字;好=实测时序/截图/文件;不许"应该没问题" |
| 文档随代码走 | 设计文档、接口定义、README 与代码同库同评审;改行为必改文档;运行时产物先入 gitignore 再开工 |

## 6. 反模式清单(每条都对应过真实事故)

| 反模式 | 正确做法 |
|--------|----------|
| 改完跑旧用例绿了就算修好 | 先写验证用例证明红(必要时 stash 修复验证红),再实现到绿 |
| 黑盒测试 import 源码/内部函数 | 黑盒只用命令行/脚本/请求驱动,断言在外表面 |
| 集成测试打桩、链路断在中间 | 集成直达数据层,断言落库落盘内容 |
| 单元测试翻数据层断言 | 单元断言只到函数返回值/异常 |
| 绕过公开入口测私有方法 | 私有逻辑提炼为设计文档定义的公开纯函数再测 |
| 断言值无出处("看起来对") | 断言值必须能指认:哪个返回值、响应体哪个字段、哪个持久化字段 |
| 先实现后补测试 | 顺序不可协商:P1 测试 → P2 核对 → P3 实现 |
| 方案没审就动手 | 审核是硬门,人类说"过"才算过 |
| 静默降级/兜底 | 报错要显式;降级必须设计文档预先定义 |
| 顺手改相邻问题 | 记录上报,另起范围,不混做 |
| 测试不合理时私改测试迁就实现 | 立即停手上报,由人类决策 |
| 有 UI 的改动不看效果 | 必实盘走一遍,截图留证 |

## 7. 模板

### 7.1 测试设计模板(每条用例一行,五要素齐全)

```markdown
| 用例编号 | 测试场景 | 测试前提 | 测试步骤 | 测试预期结果 | 断言代码(断什么/由什么直出) |
|---------|---------|---------|---------|-------------|---------------------------|
| TC-X-01 | | | 1. 2. 3. | | |
```

层级归属必须标注:[黑盒] / [集成] / [单元],并符合第 3 节各自边界。

### 7.2 三阶段汇报模板

```markdown
- P1:收集 N 用例通过;新用例 X 红(全部落在未实现行为),旧用例 Y 绿无误伤
- P2:逐用例核对表(用例→入口→断言出处→五要素),不一致 0 项
- P3:实现一次/第 N 次通过,全量 M 用例全绿
- 实盘验收:<步骤→证据(截图/日志/计时)>
```
