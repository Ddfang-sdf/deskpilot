# ISS-0008：性能优化——启动开销、审批阻塞全服务、截图与 UIA 成本、资源占用

| 项 | 内容 |
|----|------|
| 问题单号 | ISS-0008 |
| 标题 | MCP 响应慢：onefile 冷启动、OCR 急切初始化、单线程 daemon 被同步审批整体阻塞、双屏全桌面 PNG 证据图、UIA 属性逐个 COM 往返 |
| 严重级 | 高（影响所有真实使用场景的响应速度与资源占用） |
| 状态 | **已关闭**（2026-08-29 验收通过：234 用例全绿 + 实盘审批挂起期 /health 38~69ms） |
| 提出 | 2026-08-29（实盘使用反馈：感觉 MCP 反应慢） |

## 1. 问题现状

实测与代码走查确认以下成本点（均为当前 v0.3.0+ 行为）：

| # | 成本点 | 实证 | 影响 |
|---|--------|------|------|
| C1 | **单线程 HTTPServer 被 L3 同步审批整体阻塞** | `httpd.py:42` 使用裸 `HTTPServer`（单线程串行）；ISS-0003 后 L3 审批在 handler 内**同步等待人类裁决最长 60s**（approval_ttl） | 审批等待期间 daemon 对**一切**调用（含 L0 截图/取光标）无响应，客户端表现为"卡死/断开"；多客户端同时用直接排队 |
| C2 | **RapidOCR 急切初始化** | `main.py:199` 每个进程（daemon、每个 stdio 客户端）启动即 `RapidOCR()`，加载 ONNX 模型 ~1-3s、常驻内存 ~150-300MB | 冷启动慢；从未调过 ocr 的会话也白付内存 |
| C3 | **弹窗子进程每次 onefile 冷解压** | 审批/冻结弹窗各拉起一次 111MB exe（_MEI 解压 ~1-4s），L3 弹窗出现前用户干等 | 审批窗出现延迟 2-5s；窗口期还放大 ISS-0006 类竞态 |
| C4 | **证据截图：双屏全桌面 PNG ×2/次写操作** | `_evidence_shot`（executor/core.py:590+）取 `monitors[0]` 全域（双屏 ~5120×1440），PNG 编码 | 单次写操作附加 ~0.5-1.5s 编码耗时；审计目录无界增长（磁盘占用无上限） |
| C5 | **UIA 属性逐个 COM 往返** | get_ui_tree/get_clickable_map/_find_elements（core.py:99/165/278/319）对每节点读 4-5 个属性，无 CacheRequest 批量 | 大窗口枚举 800 节点 ≈ 数千次 COM 往返，秒级 |
| C6 | **onefile 体积 111MB** | spec 无 excludes；mcp 依赖链带入 uvicorn/opentelemetry/jsonschema 等无关钩子的全量子模块 | 每次解压耗时与临时目录 I/O；健康检查冷探也变慢 |
| C7 | **50ms tick 每拍解析共享状态文件** | corner_loop 每 50ms `check_reset_request` + `sync_local_with_shared_state` 各读一次 estop-state.json（ISS-0006 协议） | 每进程 40 次/秒 文件 IO+JSON 解析（单项小，纯属白付） |

## 2. 根因分析

| # | 根因 | 说明 |
|---|------|------|
| R1 | **传输层单线程 + 业务层长阻塞共存** | HTTPServer 单线程语义与 ISS-0003 同步审批（长阻塞）直接冲突，是"慢/卡"的最大单一来源。 |
| R2 | **启动路径做了非必需工作** | OCR 模型在启动时而非首次使用时加载（急切初始化）；弹窗每次新建进程而非复用。 |
| R3 | **取证粒度与存储格式未按用途选择** | 证据图用于回溯与审批展示，全桌面 PNG 远超所需（目标窗口区域 + JPEG 足够）；无保留策略。 |
| R4 | **UIA 访问未利用批量缓存协议** | UIA CacheRequest 可将"子树 + 属性集合"打包为单次 COM 调用（官方为跨进程枚举场景设计），未使用。 |
| R5 | **打包未做裁剪** | spec excludes 为空，PyInstaller 钩子把无关框架子模块一并打入。 |

## 3. 整改方案

### 3.1 总体

**先消灭阻塞，再削启动，后压常规路径成本。** 每项附可测的时延/体积预算；功能语义零变更
（232 用例全部保持绿色为准入）。

### 3.2 整改项（按收益排序）

| 项 | 内容 | 预期收益 |
|----|------|----------|
| P1 | **daemon 改 ThreadingHTTPServer + 写路径互斥锁**：`http.server.ThreadingHTTPServer` 替换 HTTPServer；L0 读路径全并行，写操作（过强制层者）经进程内写锁串行，审批等待不再阻塞其他请求 | 审批期间 L0 调用 < 1s；消除"卡死"感主因 |
| P2 | **OCR 懒加载**：`main.py` 不再急切 `RapidOCR()`；executor._ocr_engine 改为首次调用时初始化（带一次性锁），初始化失败记忆化报错 | daemon/stdio 冷启动 -1~3s；无 OCR 用途会话省 150-300MB RSS |
| P3 | **证据图改为"目标窗口区域 + JPEG 质量 80"**：写操作 before/after 优先取绑定窗口矩形（无绑定才退回全桌面）；格式 PNG→JPEG；新增审计保留策略（默认保留 14 天，policy 可配，启动时惰性清理） | 单次写操作附加耗时 -50~80%；审计磁盘占用有界且降一个数量级 |
| P4 | **UIA CacheRequest 批量枚举**：get_ui_tree/get_clickable_map 的元素枚举改用 uiautomation CacheRequest（子树+所需属性一次取回） | 大窗口元素枚举 5~10× 提速（数千 COM 往返 → 个位数） |
| P5 | **打包裁剪**：spec excludes 增加 uvicorn/opentelemetry/setuptools 等无关钩子产物；评估 onedir 形态供 daemon 与弹窗（onefile 仅保留给 Release 分发） | exe 体积 -20~40%；冷解压 -30~50% |
| P6 | **弹窗免进程化（二选一）**：a) 弹窗逻辑以专用 Tk 线程常驻 daemon 内（子进程零开销）；b) 独立迷你弹窗 spec（仅 tkinter+PIL，~15MB）。评审时定夺（倾向 a，需 Tk 线程安全纪律：一切 Tk 调用只在该线程） | 弹窗出现延迟 2-5s → <300ms；每次弹窗省 ~100MB 瞬态内存 |
| P7 | **状态文件 mtime 快路**：50ms tick 先 stat 比较 mtime，未变则跳过读取与解析 | 每进程省 40 次/秒 文件 IO |
| P8 | **daemon idle 自停与人类豁免**（借鉴 agent-browser daemon.rs 的 IdleActivity 设计）：daemon 记录最近活动时间（每次 /call 与本地人类动作重置），`idle_timeout_minutes`（默认 0=禁用，可配）超时自动退出；**冻结中、L3 审批等待中、存在有效绑定期内一律豁免**——防止忘关的 daemon 与常驻内存挂数天，又不误杀人类还在用的会话 | 闲置资源占用归零且无安全风险 |

### 3.3 约束

- P1 的写锁范围必须精确：强制层四道闸+执行+审计落盘段；不得把 L0 只读路径卷入锁。
- P2 懒加载不改变 ocr 工具的错误语义（引擎不可用仍显式报错，INV-7）。
- P3 证据图格式变更需同步更新审计读取侧（回放工具按扩展名解码）。
- P6 若选 a)：Tk 只允许单线程访问的纪律写入详细设计，并提供线程内隔离兜底（弹窗异常不影响 daemon）。

## 4. 测试方案

### 4.1 单元（先行）

| 用例 | 断言 |
|------|------|
| P1 并发 | 一个线程发起长阻塞调用（fake 审批等待 5s），另一线程 /health 与 L0 get_cursor 均在 1s 内返回；写锁下两次写调用严格串行（时序记录不交叠） |
| P2 懒加载 | 装配后 `_ocr_engine` 未初始化（无模型加载计数）；首次 ocr 调用触发恰好一次初始化；失败路径错误码不变 |
| P3 证据图 | 有绑定时 before/after 图为绑定窗口区域尺寸且为 JPEG；无绑定回退全桌面；清理函数只删超龄文件 |
| P4 枚举 | 同一 fake 树两次实现返回结构逐字段一致；COM 属性读取调用计数 ≤ 节点数/块大小 |
| P6 弹窗 | 弹窗请求到窗口可见 < 300ms（fake Tk 时钟）；弹窗异常不波及 daemon /health |
| P7 快路 | mtime 未变时读取函数调用计数为 0；变化后重新解析 |
| P8 idle 自停 | 注入活动时钟：超时后 daemon 收到退出信号；冻结/审批/有效绑定期间计时被重置或不触发退出 |

### 4.2 集成验收

- 全量 pytest 绿（现有 222 + 新增）
- 基准对比（同一机器）：daemon 冷启动、/call L0 p95、L3 审批窗出现延迟、写操作总耗时、daemon RSS——整改前后各采 10 次取中位数记录入库
- 双客户端并发：一个客户端停在 L3 审批窗，另一个连续 10 次 L0 调用全部 < 1s

## 6. 接口定义（SDD 公开入口；测试只允许调用以下入口）

### httpd（P1 / P8）

| 入口 | 签名 | 语义 |
|------|------|------|
| `HttpDaemon.__init__`（行为变更） | `(ctx, host=DEFAULT_HOST, port=DEFAULT_PORT, estop=None, idle_timeout_s: float = 0.0)` | 内部改用 `ThreadingHTTPServer`；L0 只读请求并行服务；过强制层的写请求经进程内写锁串行；`idle_timeout_s>0` 时启用 idle 自停，0 为禁用（默认） |
| `HttpDaemon.start` | `() -> None` | 行为同 §3.2-P1/P8；端口占用仍抛 RuntimeError（ISS-0006 §6 不变） |
| `HttpDaemon.last_activity`（新增，测试观测口） | `-> float` | 最近一次活动（/call 或急停动作）的时钟读数 |
| `HttpDaemon.idle_stopped`（新增，测试观测口） | `-> bool` | 是否因 idle 超时而停止 |
| `HttpDaemon.stop` | `() -> None` | 行为不变 |

### executor / main（P2 懒加载 / P3 证据图 / P4 枚举）

| 入口 | 签名 | 语义 |
|------|------|------|
| `Executor.ocr_factory`（新增，公开属性） | `Callable[[], Any] \| None` | OCR 引擎工厂；`ocr()` 首次调用时惰性调用恰好一次构造引擎；None 时按 main 装配的默认工厂 |
