# ISS-0001：MCP 服务无常驻进程，每次调用重新启动

| 项 | 内容 |
|----|------|
| 问题单号 | ISS-0001 |
| 标题 | 每次调用重新拉起服务进程，无常驻形态，状态不保留，效率低 |
| 严重级 | 高（影响所有真实使用场景） |
| 状态 | 已关闭（验收通过：跨进程绑定保持，单次调用 1.2s，161 测试全绿） |
| 提出 | 2026-08-17（A 机实盘使用反馈） |

## 1. 问题现状

1. **每次调用都启动新进程**：通过 `scripts/mcp_call.py` 或短生命周期 MCP 客户端调用时，
   每次会话都执行 `python -m deskpilot` 完整启动流程（策略加载 → 审计初始化 → 急停监听 →
   模块装配 → stdio 握手），实测单次冷启动约 2~4 秒；连发 N 次调用 = N 次全量启动。
2. **内存状态全部丢失**：绑定表、审批令牌、SoM 映射缓存均为进程内内存态（按设计 §6.9/§7.9/§9.9），
   进程退出即清空。实盘任务中每次重启后必须重新 attach、重新取 SoM 图，交互链断裂。
3. **急停状态不连续**：冻结标志是进程内原子变量，进程重启后急停状态复位——
   人类按下的急停无法跨调用保持。
4. 实盘影响：A 机副业任务期间，批量驱动共重启服务进程数十次；夜间执行中
   绑定失效导致的重复 attach 与定位失败占调试时间大头。

## 2. 根因分析

| # | 根因 | 说明 |
|---|------|------|
| R1 | **内部 HTTP 常驻服务设计未实现** | 总体设计 §2.1 与详细设计 §3.2 明确规划了
"内部 HTTP 仅绑 127.0.0.1" 的常驻服务，但 M1 交付时只实现了 MCP stdio 一种形态（`serve()` 阻塞于 stdio）。 |
| R2 | **MCP stdio 生命周期=会话级** | stdio 传输的服务器进程随客户端会话起止；批处理客户端（mcp_call.py）每次新建会话，必然触发 R1 的冷启动。这是协议特性，不是缺陷，但需要常驻形态承接。 |
| R3 | **状态模型为纯内存** | 绑定/令牌/SoM 缓存的失效语义与"进程重启即清空"耦合；常驻进程是让这些语义自然成立的前提。 |

## 3. 整改方案

### 3.1 总体

新增**常驻 HTTP 服务形态**（实现设计文档早已规划的内部 HTTP），MCP stdio 形态升级为
**瘦代理**（探测到常驻服务则转发，否则回退本地直跑），批处理客户端默认走常驻服务。

```
                 ┌─────────────────────────────┐
 MCP 客户端 ──→ │ mcp_server（stdio）           │
 (Kimi Code 等) │  └ 探测 127.0.0.1:9410       │
                 └───────┬──────────┬──────────┘
                   在则转发 │          │ 不在则本地直跑（兼容回退）
                 ┌────────▼────────┐ │
                 │ httpd 常驻服务   │◄┘
                 │ (ToolContext 唯一所有者)│
                 └────────────────┘
  scripts/mcp_call.py ──POST /call──→ httpd
```

### 3.2 整改项

| 项 | 内容 |
|----|------|
| A | 新增 `deskpilot/httpd.py`：基于 stdlib `http.server` 的常驻服务（零新依赖），持有唯一 ToolContext；端点 `GET /health`、`POST /call`（body=tool+params，走 tools.call_tool 全链路：强制层/审计/执行层不变）；启动/停止/线程模型；端口与审计目录沿用 policy.yml |
| B | `deskpilot/main.py` 增加 `--daemon` 模式：装配 ctx → 启动 httpd → 阻塞；缺省仍是 stdio MCP |
| C | `deskpilot/mcp_server.py` 启动时探测常驻服务：在线则切换为 HTTP 后端转发（调用语义与本地一致，返回结构化 ToolResult JSON）；不在线则保持现有本地直跑（兼容无 daemon 场景） |
| D | `scripts/mcp_call.py` 适配：`__batch__`/单次调用默认先探测 daemon；新增 `scripts/daemon.py` 快捷启动脚本 |
| E | 状态语义明确（写入文档）：常驻形态下绑定/令牌/SoM 缓存为单用户本地共享（localhost 语义）；绑定超时与 SoM 60 秒过期机制不变 |

### 3.4 约束（fail-closed 保持）

- 常驻服务只绑 127.0.0.1；无鉴权设计不变（单用户本机场景，威胁模型 §0 不防作恶）
- 代理转发只是传输层替换；强制层四道闸、审计、急停在常驻进程内原样执行
- 回退路径必须与常驻路径行为一致（同一套 tools.call_tool）

## 4. 测试方案

### 4.1 单元（Prompt 1 先行）

| 用例 | 断言 |
|------|------|
| httpd /health | 200 + status 字段 |
| httpd POST /call 放行路径 | 工具调用落到 ctx（fake ToolContext 记录），返回结构化结果 |
| httpd POST /call 拒绝路径 | 错误码透传（NO_BINDING 样例） |
| httpd 状态跨调用保持 | 同一 daemon 实例两次调用共享 ctx（fake ctx 计数单调增） |
| 探测函数 | 真实端口监听 → True；未监听 → False（超时受控） |
| MCP 后端选择 | daemon 在线 → 转发后端（fake HTTP server 收到请求）；离线 → 本地直跑（tools.call_tool 被调） |
| 回退语义 | 转发失败 → 明确错误返回（不静默） |

### 4.2 集成验收

- 全量 pytest 绿（现有 149 + 新增）
- 实盘：启动 daemon → 两次独立 mcp_call 调用共享绑定（第二次无需 attach）→
  冷启动对比：首次约 2-4s，后续调用 < 0.5s → 急停后经另一客户端调用返回 EMERGENCY_STOP（跨会话状态生效）
