## 1. 现象与证据(2026-09-10 亲验)

`sdfang` 实测:AI 发起移出白名单,弹框出现在**屏幕右上角**,与其余弹窗
(审批弹窗、冻结卡——均为"跟随目标屏右下角")观感不一致。

代码定位:

| 位置 | 事实 |
|------|------|
| `deskpilot/whitelist_window.py:632` | `win.geometry(f"{_WIDTH}x130+{win.winfo_screenwidth() - _WIDTH - 16}+40")` — **E3 撤回确认窗**(「AI 请求将 XX 移出白名单」/ [移出][保留]) ← **sdfang 看到的就是这个** |
| `deskpilot/whitelist_window.py:566` | 同一写法 — **撤销 toast**(「已撤销,已移出白名单」) |
| `deskpilot/whitelist_window.py:469` | `win.geometry("560x560")` — 白名单管理窗,无位置参数(交给 WM 自定,不在本单) |
| `deskpilot/approval_dialog.py:96` | 改造后正确写法:`_toast_placement(target_screen, _WIDTH, height)` → 目标屏右下 |
| `deskpilot/freeze_dialog.py:171-176` | 改造后正确写法:按 `target_screen` 算,屏内滑入 |

### 1.1 为什么是右上角

`winfo_screenwidth()` 在 Tk 语义下返回**主屏宽度**,`-_WIDTH-16` 定位到主屏
右边缘内侧,`+40` 是写死的顶部偏移 —— 合起来就是"主屏右上角"。
`_toast_placement` 则是"目标屏右下角",**两套语义**。

### 1.2 跨屏时的真实风险

当前双屏实测环境 主屏 [0,0,1920,1080] + 副屏 [1920,-1,3840,1079]
(手工测试记录批次 H)下 `winfo_screenwidth()`=1920,落位 x≈1484,**仍在主屏内**
——所以这次只是观感不一致。但公式本身是错的:

- 若副屏接在**左侧**(笔记本+外接屏放左边的常见布局),虚拟桌面 x 负半区才是副屏,
  主屏仍是原点屏,公式**恰好还算得对**——纯属侥幸;换成"副屏在下/上"的
  纵向堆叠布局,`winfo_screenheight()` 同理出错;
- 若枚举出的主屏不是虚拟桌面原点屏(P0 不在 (0,0)),公式直接错位;
- 撤回确认窗是**人类安全裁决面**:15s 倒计时走完按"保留"收场,
  fail-safe 方向不倒向危险,但**人类裁决权被落位剥夺**——这是真实可用性缺陷,
  不只是观感。

## 2. 根因

**ISS-0007 改造没覆盖到白名单弹窗**——不是修复引入,是设计引入:

- ISS-0007 单 §1.1 原文已点名根因 R1:"弹窗落位写死主屏……两个弹窗进程都以
  主屏尺寸求右下角"——**原文自己写的是"两个弹窗"(审批/冻结)**,
  白名单弹窗从未进入该单范围;
- §3.2 方案 B 也只定义了审批窗与冻结窗的跟随规则;
- 结果:白名单弹窗的 `winfo_screenwidth()` 写死原样留在原地,
  而同文件的其余弹窗已收敛。落位数学因此**三处手写**
  (approval 单点 / freeze 内联 / whitelist 硬编码),已由 ISS-0058 记其两处。

> 判定依据:`git log --follow deskpilot/whitelist_window.py` 显示该文件最后三次
> 改动均与 ISS-0007 无关(ISS-0012 扩展批次及其 UI 迭代),ISS-0007 从未触碰它。

## 3. 改法(方向)

- 撤销确认窗(632)、撤销 toast(566)改用统一落位;语义按既有约定:
  **E3 撤回确认窗 = 人类裁决 → 跟随"被裁决对象"所在屏右下角**
  (与审批弹窗同族:能定位进程/窗口则跟随,不能定位退主屏右下);
  **撤销 toast = 回执类 → 与撤销确认窗同屏同锚点**(人刚在这儿做的裁决,
  回执就该在这儿出现);
- 与 ISS-0058 的 `deskgeo.py` 落位单点收敛同批做;本单是**该收敛的新发现现场**,
  且严重级更高,**先行**;
- 约束:审批弹窗与冻结卡的**现有落位像素不得变化**(截图基线比对);
- 约束:单屏行为不变(与 ISS-0007 §3.3 同款)。
