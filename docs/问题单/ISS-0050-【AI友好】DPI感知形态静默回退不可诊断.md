# ISS-0050:【AI友好】DPI 感知形态静默回退——_DPI_MODE 设置后无处可查

| 项 | 内容 |
|----|------|
| 问题单号 | ISS-0050 |
| 标题 | _set_dpi_awareness() 返回 pmv2/v1/none 三态(main.py:17-41),但返回值从未被消费:不进启动审计、不进 /health、不进任何工具响应——V2 声明失败静默回退 V1(混合 DPI 副屏位图拉伸)甚至 none(坐标全面虚拟化),出问题时无任何线索可诊断 |
| 严重级 | **低**(可诊断性缺口;不影响正确路径,但违背 AI-first 可诊断原则——出问题时 AI 与人类都无从判断当前 DPI 形态) |
| 状态 | **已修复(4 用例绿:TC-50-01~04)** |
| 提出 | 2026-09-10(sdfang 问"不同分辨率截屏会有问题么",代码核查发现:_DPI_MODE 仅赋值于 main.py:41,全库无读取点) |

## 1. 背景(取证)

- `main.py:41` `_DPI_MODE = _set_dpi_awareness()` —— 全库唯一出现;
- 启动审计「服务启动」(main.py:422/431)不含 DPI 形态;
- `/health`(httpd.py:234)只回 `{"status":"ok"}`。
- 风险场景:混合 DPI 主机上 V2 回退 V1 → 副屏截图位图拉伸、键鼠与 UIA
  坐标错位(ISS-0007 实盘教训),而表象只是"AI 点不准"——无从定位。

## 2. 整改方案

| 项 | 内容 |
|----|------|
| A | 启动审计「服务启动」明细附带 DPI 形态(pmv2/v1/none) |
| B | /health 响应增加 `dpi_mode` 字段(与 status 并列;AI 可随时自查)。回报域随 ISS-0051 查询制扩为 pmv2/pmv1/v1/unaware/unknown |

### 约束

- 不改 DPI 声明逻辑本身(优先级与回退顺序不变);
- /health 只增字段不改既有字段(向后兼容);
- 测试设计(五要素):替身强制 V2 失败 → V1 路径被走+审计含 "v1"(直出);
  /health 响应含 dpi_mode 字段且值∈{pmv2,v1,none}(直出)。
