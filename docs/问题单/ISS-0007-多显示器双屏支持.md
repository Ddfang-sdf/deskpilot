# ISS-0007：多显示器（双屏）支持

| 项 | 内容 |
|----|------|
| 问题单号 | ISS-0007 |
| 标题 | 双屏场景下：审批/冻结弹窗出现在主屏导致"看不到"；截图与坐标跨屏语义未定义导致"看不全" |
| 严重级 | **高**（弹窗不可见 → 审批超时默认拒绝/急停无感知，安全通道失效；截图与坐标错位 → 工具不可用） |
| 状态 | 已批准（2026-08-29 sdfang 审核通过，挂账待开工） |
| 提出 | 2026-08-29（双 27 寸显示器实盘反馈） |

## 1. 问题现状

1. **弹窗"看不到"**：L3 审批 toast 与冻结通知 toast 固定出现在**主屏右下角**
   （`approval_dialog.py:80`、`freeze_dialog.py:161-162` 均以 `winfo_screenwidth/height`
   计算落位，Tk 该值只返回**主屏**尺寸）。用户在副屏工作时根本看不到弹窗，
   审批静默超时默认拒绝（fail-closed 语义下操作失败原因对用户不可解释），
   冻结事实也无感知。
2. **坐标"看不全"**：全屏截图取 `mss.monitors[0]`（虚拟桌面全域，
   `executor/core.py:571`），双 27 寸时图像 ~5120×1440；但窗口矩形、元素坐标、
   鼠标坐标在虚拟桌面坐标系中**可能为负**（副屏在主屏左/上方时），设计文档
   从未定义跨屏坐标语义，调用方（AI 模型）无法可靠理解"哪个像素在哪个屏"。
3. **落点校验隐含单屏假设**：`_check_point`（executor/core.py:543 起）按绑定窗口
   矩形校验点击落点；绑定矩形本身可为负坐标，但模板匹配/拖拽/SoM 编号点击等
   路径未做跨屏一致性声明，副屏居左时存在落点被误判出界的风险。
4. **混合 DPI 未对齐**：`SetProcessDPIAware`（main.py:15-20）是 V1 系统级 DPI 感知；
   双屏 DPI 不同时（如 27" 4K@150% + 27" 2K@100%），进程在副屏被系统位图拉伸，
   坐标映射再次错位（此前已有 150% 缩放实盘教训）。
5. **急停甩角语义模糊**：触发角为虚拟桌面 (0,0)（estop.py:16-17），双屏下该点
   固定在主屏左上角；副屏居左时，用户甩到"最左上角"（副屏）反而不触发。

## 2. 根因分析

| # | 根因 | 说明 |
|---|------|------|
| R1 | **弹窗落位写死主屏** | 两个弹窗进程都以主屏尺寸求右下角，从未枚举显示器，更没有"跟着目标窗口/鼠标所在屏走"的策略。Tk 无多屏 API，须用 Win32 枚举。 |
| R2 | **坐标系语义未定义** | 截图、窗口矩形、鼠标、元素框全部使用虚拟桌面坐标（含负值），但工具返回结构没有坐标系说明，模型只能猜；负坐标还可能在落点校验、模板匹配偏移计算中被当作非法值。 |
| R3 | **DPI 感知级别错误** | V1 系统级感知在混合 DPI 双屏下副屏坐标失真；正确形态是 Per-Monitor V2（`SetProcessDpiAwarenessContext(-4)`）。 |
| R4 | **触发角写死 (0,0)** | 甩角判定以虚拟桌面原点为触发区，未按"用户最习惯的角落"定义；多屏下应有明确且文档化的角落语义。 |

## 3. 整改方案

### 3.1 总体

引入**显示器枚举与"目标屏"概念**：所有面向人类的 UI（审批窗、冻结窗）出现在
**相关屏**（审批 = 目标窗口所在屏；冻结 = 鼠标所在屏）；所有面向 AI 的坐标
统一声明为**虚拟桌面坐标系**并保证负坐标全链路合法；DPI 感知升级 Per-Monitor V2。

### 3.2 整改项

| 项 | 内容 |
|----|------|
| A | **新增显示器枚举纯函数**（executor 或新 monitor 模块）：`enum_monitors() -> list[dict]`（rect/work_area/is_primary，经 Win32 EnumDisplayMonitors + GetMonitorInfo）；`screen_of_point(x, y)`、`screen_of_rect(rect)` 纯函数（含负坐标）。 |
| B | **弹窗跟随相关屏**：审批 toast 落位改为"目标窗口所在屏的右下角"（无绑定时回退鼠标所在屏）；冻结 toast 落位改为"鼠标所在屏的右下角"。Tk 落位坐标按该屏 work area 计算（Tk 几何同样接受虚拟桌面坐标）。 |
| C | **坐标系声明与负坐标合法化**：工具返回结构补充坐标系字段（`coord_space: "virtual_desktop"`，文档化含负值）；`_check_point` 与模板匹配/拖拽偏移计算按虚拟桌面全域校验（取代任何 ≥0 隐含假设）；`fullscreen` 返回 monitors[0] 全域并附每屏边界列表（`monitors: [...]`），AI 可直接定位"第几屏"。 |
| D | **DPI 感知升级 Per-Monitor V2**：启动时优先 `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`，失败回退现有 V1（兼容老系统）；混合 DPI 下 UIA 矩形/键鼠/mss 坐标三者同系验证。 |
| E | **急停角落语义文档化**：维持虚拟桌面 (0,0) 触发区（主屏左上角），在 README/详细设计写明"触发角为主屏左上角"；策略项预留可配置角落（本单不实现，仅文档）。 |

### 3.3 约束

- 单屏行为逐像素不变（枚举得 1 屏时所有新逻辑退化为现状）。
- 弹窗跟随只改落位计算，审批/冻结的文件协议与消费链路不动。
- 不引入新第三方依赖（Win32 经 ctypes；mss 已具备枚举能力，优先复用）。

## 4. 测试方案

### 4.1 单元（先行）

| 用例 | 断言 |
|------|------|
| 枚举解析 | 注入双屏 rects（主屏 (0,0,2560,1440)，副屏 (-2560,0,0,1440)）→ enum 结果含 2 屏且主屏标记正确 |
| 目标屏判定 | screen_of_point(-100, 100) → 副屏；screen_of_rect(跨越两屏的窗口) → 面积占比大者所在屏 |
| 弹窗落位 | 目标窗口在副屏 → toast x 落入副屏 work area；无绑定 → 鼠标屏 |
| 负坐标合法化 | _check_point 对副屏负坐标落点不误判出界；模板匹配命中点含负坐标时偏移计算正确 |
| fullscreen 返回 | 含 coord_space=virtual_desktop 与 monitors 列表（长度=枚举屏数） |
| DPI 回退 | 注入 SetProcessDpiAwarenessContext 失败 → 走 V1 路径且启动不失败 |

### 4.2 集成验收

- 全量 pytest 绿（现有 222 + 新增）
- 双屏实盘：副屏前台工作，触发 L3 审批 → toast 出现在副屏右下角；甩角冻结 → 冻结窗出现在鼠标所在屏
- 双屏实盘：副屏居左（负坐标）时 attach 副屏窗口并点击元素 → 落点正确
- 单屏回归：现有验收序列（ISS-0006 §4.2）逐条不变
