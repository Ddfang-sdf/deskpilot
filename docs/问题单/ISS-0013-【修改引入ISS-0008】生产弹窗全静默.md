| 项 | 内容 |

| 问题单号 | ISS-0013 |

| 严重级 | **极高（P0）**：安全感知通道全哑——审批不可见 → 超时默认拒绝（fail-closed 下操作无理由失败）；冻结无感知 → 用户不知已冻结、不知如何复位；已随 v0.3.0/v0.3.1 发布 |

## 1. 问题现状

1. **接线遗漏（根因点）**：`dialog_service.py:25` `self._factory = window_factory`，
   生产装配默认 `window_factory=None` → `_factory` 为 None；`_dispatch`
   （`:79`）调用 `None(kind, payload)` 抛 TypeError，被"弹窗异常不波及调用方"
   的 except **静默吞掉** → 窗口永不出现，无任何留痕。`_default_factory`
   方法存在但**从未被接线**。
2. **实盘实证链（2026-08-31 全程取证）**：
   - daemon 发起 `launch_app calc.exe`（入白审批）→ 60s 超时；desc 文件写出、
     **result 文件从未产生**（窗口从未运行倒计时）；
   - 常规 L3 审批（绑定记事本后发 alt+f4）同样无窗超时——**非入白特有**；
   - 截图实证：屏幕无任何弹窗；UIA 枚举顶层窗口无 DeskPilot 窗口；
   - 主线程直调 `_default_factory` 建窗成功、geometry 轨迹正常
     （480x216@(1424,752)）——**只有服务线程路径是死的**，排除建窗代码本身。
3. **历史实证**：2026-08-29 18:34 甩角冻结（estop-state.json seq 27）无任何
   冻结感知窗弹出，遗留冻结状态两天、用户不知如何复位——与本根因完全吻合。
4. **影响版本与形态**：ISS-0008（bb20c6b）起全部构建，**含已发布的
   v0.3.0 / v0.3.1**；daemon 与 stdio 全中（TkApprovalChannel / FreezeNotifier
   只要持有 dialog_service 就走线程路径，子进程弹窗路径被跳过）。

## 2. 根因分析

| # | 根因 | 说明 |
|---|------|------|
| R1 | **装配接线遗漏** | `__init__` 未将 `_default_factory` 设为缺省（缺 `or self._default_factory`）；默认路径 `_factory=None`。 |
| R2 | **静默吞异常零观测** | `_dispatch` 的容错 except 吞掉 TypeError，无审计无 stderr——通知层故障完全隐形。 |
| R3 | **测试结构盲区** | 全部单测经 `window_factory` 注入替身，真实默认路径（None→_default_factory）零覆盖；ISS-0008 实盘验收以 /health 延迟为代理证据，**未目视弹窗**。 |

## 3. 经验总结（修改引入复盘与预防）

### 3.1 为什么测试设计没拦住（机制层真因）

1. **测试设计围绕"组件内部分支"，从不围绕"装配矩阵"**：P6 的用例（队列循环 /
   Tk 循环 / 延迟观测 / stop 幂等）全部是"**给定工厂之后**组件的行为"；缺陷不在
   组件逻辑，在**默认装配**。测试设计从未枚举"生产环境有几种装配形态、每种谁
   守门"——组件测得再细，装配是瞎的。
2. **桩打在了缺陷居住的那一层**：`window_factory` 是测试缝，测试全从缝进入；
   "`_default_factory` 由谁接上"这段**选择逻辑**恰好是被 mock 替代掉的部分。
   **mock 在哪一层，哪一层就失明**——在选择逻辑上打桩=放弃该路径的覆盖。
3. **缺少"装配守门"测试类型**：`get_dialog_service()` / `main()` 这类"入口产生
   对象图"的代码没有任何形态断言。一行 `assert get_dialog_service()._factory
   is not None` 即可拦截的缺陷，因没有该测试类型而漏网。
4. **优化单没有"路径变迁"视角**：P6 引入选择器 `dialog_service is not None ?
   线程窗 : 子进程窗`；生产恒真 → 子进程路径死，线程路径未接线也死 → **全黑**。
   测试设计若先画"旧路径/新路径/选择器"三列，就必须回答"选择器每个分支由哪条
   用例走"，一问即露。
5. **验收用代理指标冒充终效应**："/health 38~69ms" ≠ "弹窗出现在屏幕上"。

### 3.2 下次测试设计的 5 条可执行检查项（每条可勾选、可举证、可打回）

| # | 规则 | 落地方式 |
|---|------|----------|
| R1 | **装配矩阵强制**：凡构造函数带默认值的注入参数、`set_X` 接线点，测试设计必须附"生产装配形态表"，每种形态至少一条**以生产默认值构造**的用例 | 设计文档缺表=门禁打回 |
| R2 | **mock 边界规则**：守门用例只许在**最末端可观察点**打桩（tk 控件/HTTP 响应/文件写）；禁止在工厂选择、通道路由等**选择逻辑**上打桩并宣称覆盖 | 每条 mock 在设计文档标注"被 mock 的选择逻辑由用例 #__ 覆盖"，填不出=打回 |
| R3 | **装配入口形态断言**：每个 `get_*`/装配入口至少一条关键链接非空断言（如 `assert get_dialog_service()._factory is not None`） | 一行成本，灭掉整类"没接线"缺陷 |
| R4 | **优化/重构单必附路径变迁表**：旧路径/新路径/选择器三列，每条路径与选择器每个分支标注对应用例编号 | 没填表不进 P1 |
| R5 | **人类可见功能的终效应断言**：验收断言点=屏幕/窗口状态（UIA 枚举或截图），禁止只断言服务内部状态 | 进各单 §4.2 验收清单硬性条款 |

> 自查：ISS-0012 测试设计同样违反 R2（DialogRevokeChannel 用替身 dialog_service、
> 托盘只测纯函数）——按 R1/R2 在本单 §5.1 补接线断言，按 R5 由实盘目视兜底。

## 4. 整改方案

| 项 | 内容 |
|----|------|
| A | **接线修复**：`__init__` 改 `self._factory = window_factory or self._default_factory`（单行；注入路径行为不变）。 |
| B | **吞错留痕**：`_dispatch` 的 except 增加 stderr 打印（容错不阻断调用方的语义不变；故障不再隐形）。 |
| C | **守门用例**：默认构造 DialogService → show() 必须触达 `_default_factory`；注入路径不回退；吞错必有 stderr（§5.1）。 |
| D | **版本声明**：v0.3.0/v0.3.1 标记受本缺陷影响；修复随 v0.3.2 发布并在发布说明中显式声明。 |

### 4.1 约束

- 仅接线与留痕两行级改动，不动弹窗协议/线程模型（最小回归面）。
- 修复后接续完成 ISS-0012 §4.2 的弹窗与撤回手工验收（同一实盘场景）。

## 5. 测试方案

### 5.1 单元（先行）

| 用例 | 断言 |
|------|------|
| 默认装配触达真实工厂 | `DialogService()` 默认构造，monkeypatch 实例的 `_default_factory` 为替身 → `show("approval", payload)` → 替身被调用且 kind/payload 直出（红：当前 NoneType 不触达） |
